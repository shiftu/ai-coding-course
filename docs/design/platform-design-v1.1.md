# AI 微课堂自适应学习平台 · 设计文档 v1.1(精简版)

> 对 v1.0 的可落地性审核结果:以"两个人 4–6 周能上线、一个人能长期维护"为标准,
> 砍掉和简化了大量前置建设,每个砍掉项都标注了"什么信号出现时再建回来"。
> 灵魂部分(行为测评、能力模型、内容即代码、隐私边界)原样保留。
> 日期:2026-08-20 · 作者:Panda(与 AI 协作产出)· 上一版:platform-design-v1.md（同目录）

---

## 0. 这次精简的三个核心判断

**① 规模错觉。** 100 人/年 = 平均每周约 2 个新人。v1.0 里不少组件是按"平台流量"设计的(打分引擎、装配引擎、金丝雀池),而真实场景是"精品小班"。每周 2 份测评用不着实时打分服务,一个批改 agent + 人工抽查绰绰有余。

**② 最大的发现:单版本策略。** v1.0 花了很大力气设计"旧版本 3–5 个共存"(version_range 变体、多版本装配)。但**平台本身就统一部署和配置所有工具**——环境是我们发的,版本就是我们定的。让全员始终用同一个标准版本,多版本课程内容的需求就整体消失了。这条需求是"公共平台思维"带进来的,内部场景下是自找的复杂度。

**③ 自动化的正确顺序。** 先让人肉流程跑通并留下数据,再自动化真正成为瓶颈的环节——而不是预先建好五段流水线等着瓶颈出现。v1.1 的原则:**每个自动化组件都要等它的人肉版本先痛过。**

## 1. 砍单:砍掉了什么、简化成什么、什么时候建回来

| v1.0 设计 | v1.1 处理 | 回建触发器(出现此信号再建) |
|---|---|---|
| 动态装配引擎(切片查询+拓扑排序) | **3 条静态轨道 + 模块免修考**(§5) | 人工调整学员路径的请求高频出现(如每周多次) |
| 多版本切片共存(version_range 变体,保留 3–5 版) | **单一标准版本**,平台统一环境即统一版本 | 平台对外开放,或公司被迫多版本并存 |
| 五段全自动更新流水线(再生成/AI 评审/金丝雀/自动发布) | **一个哨兵 cron**:版本 diff + 全量机验 + 开 Issue(附 changelog,可带草稿 PR),人工审、人工合并(§7) | 哨兵 Issue 每月 >10 条,人工修订成为明确瓶颈 |
| 新工具发现哨兵 + 自动评估卡 | 飞书群人肉发现 + Gitea「新工具提议」issue 模板 | 复盘发现明确错过重要工具 ≥2 次 |
| 200 人全员标定测评战役 | **10–15 人标定小组**(公认高手约 5 人 + 普通用户 8–10 人),专家判断校准 rubric | 需要"全公司 AI 适配度底图"向管理层汇报时,再扩大为全员活动 |
| 等级自动兑换权限(对接 llm-gateway/approval) | 等级 = 徽章 + 证据页;budget 调整由管理员看面板**手动**操作 | 等级公信力建立、且 gateway 侧打通成本确认很低时 |
| 技能续证 + 权限有效期机制 | 工具大版本发布 → 发一条增量微课通知,自愿学,无任何权限机制 | 权限自动兑换建立之后 |
| own-mac 采集器 CLI | **交付物即证据**:PR/截图贴 Gitea Issue(沿用现有训练营打卡方式) | own-mac 切片变多且交付物造假成为真实问题时 |
| 打分规则引擎服务(实时信号流水线) | **一个"批改 agent" skill**:测评/作业结束后读工件(git、shell 历史、gateway 日志、录屏)按公开 rubric 打分并附证据链接;前 20 份人工全查,之后抽查 10%(§4.4) | 批改量大到抽查失效(内部规模下几乎不会) |
| 自定义管理台 | 直接用 Gitea(PR 审核、Issue)+ 飞书通知 | 非技术背景的管理员参与日常运营时 |
| 会话录制(全程) | 仅测评沙盒录制(asciinema) | — |
| 平台埋点接 PostHog、provider 抽象层 | 推迟;先用 Gitea/gateway 自带数据 | 对外开放提上日程时 |

**原样保留、不许再砍的灵魂**:33 分钟沙盒行为测评(含埋点与 debrief)、四维能力模型 + 安全闸 + 短板决定制(纯纸面制度,零工程成本)、内容即代码、纯 TTY、隐私硬边界。

## 1.1 v1 的全部工程面(这就是要建的所有东西)

1. **一台沙盒宿主机**:Docker + 3~5 个预热容器 + 每人持久卷 + ttyd web 终端;
2. **一个小 web 前端**(4–5 个页面):飞书 SSO 登录 → 测评 → 我的轨道(课程清单+进度)→ 个人雷达图与证据页;
3. **一个测评任务仓库**:精心布置埋点的复合任务 repo(平台最值得打磨的单件);
4. **curriculum 仓库**:现有 10 课按精简 schema 拆成切片;
5. **三个 Hermes skills**:批改 agent、内容哨兵 cron、飞书答疑助教。

预估:2 人 × 4–6 周上线;上线后 1 人兼职维护(哨兵 Issue + 抽查批改 + 内容修订)。

## 2. 产品定位与原则(不变)

公司内部的 **AI 能力加油站**:自愿来、随时走。摸底(行为观察而非答题)→ 补齐(按短板给课)→ 保鲜(内容跟工具走)。平台统一完成工具部署与配置,规避"因安装配置复杂导致放弃"。

设计原则不变:行为证据优先;不监控员工(毕业即停止采集);内容即代码;纯终端。"等级兑换权限"降级为愿景——v1 里等级是徽章和证据页,权限操作人工执行。

服务对象与规模假设不变:约 100 人/年,峰值并发 30,随到随学(集中开营 = cohort 标签 + 共享飞书群 + 统一 Demo Day 日期,无额外设计)。

## 3. 能力模型(不变——纸面制度,零工程成本)

### 3.1 四维等级(L0–L4,行为锚点)

| 维度 | L1 起步 | L2 上手 | L3 熟练 | L4 沉淀 | 证据源 |
|---|---|---|---|---|---|
| **工具操作** | 环境跑通,会用一个入口 | 会选入口、会 /clear、会恢复会话 | 多工具组合、会 skill/profile | 能给别人搭环境、排障 | gateway 日志、sessions |
| **需求表达** | 一句话说清任务 | 先要计划、会收窄范围 | 五要素 spec + 可测量验收 | 带人收敛模糊需求 | session、PR/spec |
| **质量验证** | 跑一遍再说完成 | 看 diff + 有测试 | TDD + 向 AI 要证据 | 为团队建质量闸 | Gitea PR |
| **自动化编排** | 会用现成 skill | 建过能用的 cron/监控 | 委派、订阅、稳定输出 | 沉淀被复用的 skill | cron、skill 仓库 |

### 3.2 安全合规 = pass/fail 资格闸(不变)

S1 入门闸(密钥卫生、走内部网关)→ 解锁 L2 内容;S2 进阶闸(budget/approvals/泄漏处置)→ 解锁 L3;S3 生产闸(自动化兜底、成本选型)→ 解锁 L4。

### 3.3 总等级 = 短板决定制(不变)

驾照等级 = 四维最低级,且过对应安全闸。推荐逻辑因此只有一条:优先补最短的板。

### 3.4 等级获取(不变)

测评最高定到 L2;L3/L4 作品制(大作业、毕业项目、被复用的 skill);资深工程师走导师背书直升,背书留痕、导师负责。

## 4. 摸底测评(结构不变,打分方式简化)

### 4.1 33 分钟三段漏斗(不变)

自述 3 min(定沙盒起测难度,不计分)→ 快筛 10 题(只筛零基础直送 D0)→ 沙盒实操 20 min(主菜)。

### 4.2 沙盒复合任务与埋点(不变)

一道复合任务("接手这个小工具仓库:修 README 过时处 + 完成 Issue #7,提 PR"),四类埋点:模糊 Issue(测需求表达)、必挂的测试用例(测质量验证)、预埋假 key(测 S1 闸)、任务量略超时长(测范围控制)。沙盒内放速查卡(测本能不测背命令);结束必有 debrief 复盘屏,揭开全部埋点并回放关键片段——测评即第一课。

### 4.3 信号采集(简化:只留天然存在的管道)

容器 shell 历史、git 仓库状态、gateway 请求日志、asciinema 录制(仅测评沙盒)。**不建实时信号流水线**——这些数据本来就落在那里,测评结束后由批改 agent 一次性读取。

### 4.4 打分 = 批改 agent + 人工抽查(核心简化)

- 测评/作业结束后,**一个 Hermes skill(批改 agent)** 读取全部工件,按**公开的 rubric**逐行判定("提交前跑过测试 → 质量验证 +1"),输出四维向量(L0–L2)+ S1 结果 + 每条判定的证据链接 + debrief 文本;
- **前 20 份人工全查,之后抽查 10%**;判定规则全公开,支持申诉(人工复核录屏与工件);
- 每周约 2 份新人测评的量级下,这个方案的成本接近零,且比规则引擎更容易维护(改 rubric = 改一个 markdown)。

### 4.5 标定 = 10–15 人小组(替代 200 人战役)

约 5 位公认 AI 高手 + 8–10 位普通用户先跑一遍测评,用他们的批改结果人工校准 rubric 锚点(高手普遍做到的行为 → L2/L3 锚点)。个人分数仅本人可见的铁律不变。全员测评活动推迟到需要"全公司底图"汇报时再做。

## 5. 课程组织:3 条静态轨道 + 模块免修考(替代装配引擎)

四维 × 三级的组合实际收敛为很少几种典型画像,静态轨道 + 免修覆盖了个性化 80% 的价值,而内容保持线性可读、维护者心智负担极小:

| 轨道 | 进入条件 | 内容 |
|---|---|---|
| A · 零基础 | 快筛未过,或测评多维 L0 | D0 起,全部模块顺序走 |
| B · 有基础 | 测评多维 L1–L2 | 跳过入门模块,从公司工作流特有内容开始(网关、Hermes、飞书、红线) |
| C · 资深 | 导师背书直升 | 只上公司特有模块 + 大作业/毕业项目 |

**模块免修考**:每个模块开头一个 10 分钟迷你实操,通过即跳过该模块——轨道内的细粒度个性化由它完成,不需要装配算法。个人面板仍显示四维雷达图 + 最短板 + "距下一级还差哪 2 个行为"。

### 5.1 切片 schema(砍到 5 个字段)

```yaml
id: quality/verify-before-done   # 稳定 ID,路径即分类
dimension: 质量验证              # 四维之一,或 safety-gate
level_edge: L1->L2
type: demo | exercise | pitfall | quiz
env: container | own-mac
verify:                          # 可选:机验命令,哨兵 cron 与学员自检共用
  - cmd: "pytest -q"
    expect_exit: 0
```

砍掉:`tools`/`version_range`(单版本策略)、`depends_on`(轨道文件里的排列顺序即依赖)、`grading_signals`(rubric 集中在批改 agent 里维护)。切片顺序由每条轨道一个 `track.yaml` 清单文件决定,一眼可读、一行可改。

### 5.2 交付物与等级更新

沿用现有训练营方式:交付物(PR、截图、spec)贴 Gitea Issue → 批改 agent 打分 → 面板更新。仅课程期内发生,毕业即停(§8)。

## 6. 环境体系(不变,再减一件)

- **第一层:平台沙盒** —— 一台 64G 宿主机 + Docker 预热池 + 每人持久卷 + ttyd web 终端。承载测评、破坏性练习、全部 `env: container` 切片。30 并发无压力,不用 K8s、无预约调度。（2026-09-10 补:每容器硬上限 2 GiB 内存 / 512 进程,容量不再拍脑袋,`sandctl capacity` 按宿主机实际内存算硬上限与实测余量。按实测活跃沙盒约 1 GiB,64G 机器硬上限 28 人、实测约 55 人,30 并发成立。）
- **第二层:学员自己的工作 Mac** —— 一条命令的预配置脚本(D0 清单自动化);macOS 专属内容(Keychain、lark-cli)在这层完成,**证据 = 交付物本身**(不再做采集器 CLI)。
- "从空白搭建一切" = L3 认证课,在自己 Mac 上完成,成果直接带走。
- 明确不做:桌面环境、屏幕串流、Mac 池/虚拟机(否决理由见附录 A)。

## 7. 内容保鲜:一个哨兵 cron(替代五段流水线)

**单版本策略是前提**:平台环境统一发版,课程只维护当前标准版本,无多版本变体。

哨兵 cron(每周跑,一个 Hermes skill):

```
1. 版本 diff:对比工具链(claude-code/codex/hermes/lark-cli)最新版与 versions.lock
2. 全量机验:在干净容器里跑全部切片的 verify 块,列出跑不通的切片
3. 开 Issue:受影响切片清单 + changelog 链接 + (可选)AI 起草的修订 PR
4. 人工审、人工合并;合并后更新 versions.lock,沙盒镜像随之升级
```

- 安全红线内容(第 9 课范畴)的改动永远人工——这条与 v1.0 相同;
- 学员传感器保留最简形态:助教机器人收到的高频求助,由维护者手动沉淀为 pitfall 切片(自动聚类推迟);
- 新工具引入:飞书群讨论 + Gitea「新工具提议」issue 模板,管理员评估。

**升级路径**(写在这里,防止将来重新论证):当哨兵 Issue 每月超过约 10 条、人工修订成为瓶颈时,按 v1.0 §7 的设计依次补:AI 再生成 → AI 评审闸 → 自动合并低风险变更。

## 8. 数据与隐私边界(硬约束,一字不改)

| 阶段 | 采集范围 |
|---|---|
| 测评/课程期间 | 沙盒内行为信号(shell/git/gateway/录屏);own-mac 任务只看交付物 |
| **毕业之后** | **零采集、零追踪**——不读任何日常工作工件,保护行动与决策的松弛感 |
| 分数可见性 | 个人分数与证据仅本人可见;管理端只看匿名聚合 |

## 9. 运营机制(精简后)

- **同伴机制的异步替代**(随到随学的必答题):互评 → AI 助教评审 + 导师抽查;毕业演示 → 录屏 + 异步评审;社交能量 → **月度 Demo Day**(当月毕业者线上演示,兼作背书场合与讲师选拔入口);答疑 → 飞书群常驻 Hermes 助教机器人。
- **讲师轮值**沿用:senior 只录 5–10 分钟新片段。
- **管理员日常 = 三件事**:审哨兵 Issue/修订 PR、抽查批改、看匿名聚合分布定内容优先级。全部在 Gitea + 飞书里完成,无自定义管理台。

成功指标(不变):Time-to-first-PR(北极星)、切片卡壳率、等级分布迁移(匿名聚合)、内容新鲜度(发版→切片修复的时滞)。

## 10. 技术架构(v1.1)

```
┌──────────── 小 web 前端(飞书 SSO)────────────┐
│ 测评页(内嵌 web 终端)│ 我的轨道 │ 雷达图/证据页 │
└──────┬──────────────────────────┬─────────────┘
       │                          │
  沙盒宿主机 ×1                批改 agent(Hermes skill)
 (Docker 池+持久卷              哨兵 cron(Hermes skill)
  +ttyd+asciinema)             答疑助教(Hermes skill)
       │                          │
┌──────┴──────────────────────────┴─────────────┐
│        既有基础设施(全部复用,不新建)          │
│  Gitea(curriculum/作业/Issue)· llm-gateway   │
```

平台 = 既有工具链上的**薄编排层**。没有独立打分服务、没有装配引擎、没有管理台、没有消息队列。

## 11. 路线图(压缩为两个阶段 + 触发式升级)

### Phase 0 · 地基(1–2 周)

- 能力模型 rubric 定稿(四维行为锚点 + 三道安全闸清单,即批改 agent 的判定依据);
- 现有 10 课按 5 字段 schema 拆成切片,排出 3 条轨道的 track.yaml;
- 测评任务仓库布置(埋点 repo,值得花最多心思的单件)。

### Phase 1 · 上线(3–4 周)

- 沙盒宿主机 + web 前端 + 批改 agent;
- 10–15 人标定小组试跑 → 校准 rubric → 对新人开放;
- 哨兵 cron、答疑机器人、Demo Day 随后一两周内跟上。
- **里程碑:第一批真实新人走完"测评 → 轨道 → 毕业",批改抽查一致率 ≥90%。**

### 之后:触发式升级(不排期,按 §1 砍单表的触发器逐个决定)

装配引擎、自动再生成流水线、权限自动兑换、续证机制、全员标定、对外开放——每一项都等它的触发信号出现,再按 v1.0 文档(保留作为蓝图)恢复建设。

## 12. 风险与对策(精简后新增/变化项)

| 风险 | 对策 |
|---|---|
| 静态轨道不够"个性化",高手觉得被拖慢 | 模块免修考兜底;免修请求高频 = 装配引擎的回建触发器,风险自带解决方案 |
| 批改 agent 判定不稳定 | rubric 逐行公开、每条判定附证据链接;前 20 份全查校准;支持申诉人工复核 |
| 单版本策略被打破(某团队锁旧版) | 平台立场:课程只保标准版;个别团队特例由导师人工辅导,不进内容体系 |
| 哨兵 Issue 无人处理,内容悄悄过时 | 哨兵 Issue 指派轮值维护人 + 飞书提醒;新鲜度时滞进指标看板 |
| 测评被应试 | 埋点本来公开(debrief);防埋点唯一方法就是好习惯;定期轮换任务仓库变体 |
