# 记一条经验

## 什么时候触发

- 踩了坑并找到绕法
- 发现了非显而易见的事实（某个行为只在特定环境成立）
- 验证结果推翻了之前的说法（写成反例）

**没有值得留下的东西就不写。** 零记录结束是正常的，不要为了凑数把同一件事换个说法记三遍。

## 步骤

1. **先查有没有同类。**

   ```
   keel why --query <关键词>
   ```

   已有同类：补充它的适用条件，或者当你的结论与它冲突时，把冲突写清楚而不是覆盖。

2. **写候选记忆。** 一条只说一件事：

   ```
   keel note "<一句话事实>" \
     --tag <主题> --path <相关文件> --kind gotcha \
     --condition environment=<在什么条件下成立> \
     --by agent:<你是谁>
   ```

   `--kind`：`gotcha` 坑、`fact` 事实、`pointer` 外部资料、`counterexample` 反例。

3. **写清适用边界。** 「SQLite WAL 在 NFS 上锁失败」是有用的；「SQLite 有问题」不是。
   没有条件限定的记忆会在不该出现的时候被召回。

4. **能验证就当场验证。** 这条经验如果有一条命令能证伪它，就跑一次：

   ```
   keel verify M-<短前缀> -- <命令…>
   ```

   命令原样 exec，不经 shell。退出码 0 = 通过、1 = 发现违规、其余一律是错误。
   通过就把它转成 `verified` 并写下证据；失败就转 `disputed`；跑不起来两者都不是，状态不变。

   写不出验证命令是常态，那就让它留在 `candidate`。**不要为了让它变 verified 而编一条一定会通过的命令。**

## 状态说明

新记忆一律是 `candidate`：可以被检索到，但在有证据之前，不会被当成项目规则注入。

升成 `verified` 只有一条路：`keel verify` 真的跑完一次验证器。没有自述入口——
自述的通过既不能被别人重跑，也不能被撤回。

证据记下两个摘要：一个盯结论本身，一个盯 scope 覆盖的代码。
改了记忆正文，旧证据就对不上（`memory_status_unsupported`，error）；
代码变了但结论没变，证据算过期（`memory_evidence_stale`，提醒）。两种都要重新验证。

## 不要做的事

- 正文超过 20 行说明它其实是一次决策，走 `keel decide`。
- 不要删掉失败和反例，它们也是长期记忆。
