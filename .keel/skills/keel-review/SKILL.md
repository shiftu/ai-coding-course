# 受控进化

## 什么时候触发

只在**显式的维护任务**或**有边界的收尾**里跑。不要在每次普通任务后自动展开。

## 步骤

1. **读报告。**

   ```
   keel review --json
   ```

   报告里的次数**只决定审阅优先级**，不决定可信或生效。同一个错误被转述三次不是三份证据——
   `memory_cluster` 已经把同源转述折成一条了。

   `review` 只读，也不执行任何规则。规则当前过不过，跑 `keel check --target worktree`。

2. **处理到期决策。** `review_after` 到了的决策，按实际证据改状态并在正文末尾写一句原因：

   - 有相关验证证据且没有反例 → 可以提议转 `proven`
   - `decision_reverted` 候选说明它关联的提交被撤回过 → 确认结论还成不成立，不成立就用 accepted 决策替代
   - 你自己写的 proven 不构成独立验证，不要用它去换更高的自决上限

3. **处理学习候选。** 每批限量，不要无限扩展：

   - `memory_cluster`：多条同主题记忆**可能**指向同一条不变量。先自己判断是不是——
     keel 只给簇，不给结论。是的话提炼成规则，**默认 `candidate`**
   - `memory_disputed`：有反例。先处理冲突，再谈提炼
   - `rule_candidate_incomplete`：补齐它缺的那几项
   - 一条可靠事实可以长期只是事实，不必逐级变成技能

4. **给候选规则配齐三样东西**，缺一样 `promote` 就会拒绝：

   - `check.argv`：退出码约定是 `0` 通过、`1` 发现违规、**其余一律是 error**。
     目录不存在、工具没装都必须是 error，绝不能写成「通过」
   - `from`：指向一条**有效**决策。会拦住所有人提交的硬规则，得有一条说明「为什么」的决策背书
   - `cases`：`.keel/cases/<规则短 ID>/` 下的真目录，**pass 和 fail 两个方向都要有**

   只证明「该过的过了」不算对照验证——一条永远 `exit 0` 的检查也能满足。
   `expect: fail` 的夹具里放故意违规的代码，所以全仓库扫描型的脚本要排除 `.keel/`。

5. **跑对照验证。**

   ```
   keel promote R-<短前缀>
   ```

   过了就 candidate → active 并写下证据；没过就留在 candidate，失败证据同样写进仓库。
   **不要手工把 `status` 改成 `active` 绕过这一步。**

6. **发现反例或回归就撤回。**

   ```
   keel retire R-<短前缀> --reason "<为什么撤>"
   ```

   原因写进正文，历史保留。被它替代过的旧规则会被提示出来，是否恢复由你判断。
   **不要删除失败历史。**

7. **收尾。**

   ```
   keel check --target worktree
   keel sync
   ```

   一次提交，说明这批改了几条、依据是什么。

## 处理失效条目

`object_stale` 说明 scope 指向的路径已经不在了。先重定位；确实过时就归档，保留原因，不要直接删掉历史解释。
