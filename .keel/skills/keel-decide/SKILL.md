# 记录一次架构决策

## 什么时候触发

四类动作够得上决策，其余写记忆（keel-learn）：

- 加、换、删依赖
- 跨两个以上模块的结构选择
- 改公开接口或数据格式
- 改构建或部署方式

## 步骤

1. **先查先例。** 改动路径已经有人定过调没有：

   ```
   keel why --path <你要改的路径>
   keel why --query <主题关键词>
   ```

   已有决策覆盖且你只是照着做 —— 不要新建 ADR，直接在提交里引用它的完整 ID。

2. **看这次能不能自决。** `keel brief --task "<你要做的事>" --path <路径>` 里有工作流建议上限。

   - **0**：输出选项、你的倾向、影响面，等人拍板。不要替人决定。
   - **1**：只有当 `keel why` 找到适用范围内、没有失效证据的先例时才自决；否则回到 0。
   - **2**：自决并记录。

   上限由项目策略给出，不看 tag。`db` 下有三条成功先例，也不代表可以自行决定生产数据删除。
   **你自己把某条决策改成 proven 不算独立验证**，不会提高上限。

3. **写决策。** 正文四段都要写实，空 ADR 不算数：

   ```
   keel decide "<一句话结论>" \
     --tag <检索用标签> --scope '<管辖路径 glob>' \
     --status accepted --by agent:<你是谁> --body - <<'EOF'
   ## 背景
   <为什么现在要定这个>

   ## 决定
   <定了什么>

   ## 备选与理由
   <还考虑过什么，为什么不选>

   ## 后果与验证方式
   <会带来什么约束，怎么验证它还成立>
   EOF
   ```

   不确定就先留 `proposed`（默认），等人确认后再转 `accepted`。

4. **替代旧决策**要一次做完，并说明旧规则去向：

   ```
   keel decide "..." --supersedes D-<完整或短前缀> --status accepted \
     --rule-migration R-<旧规则>:retired --body - <<'EOF'
   ...
   EOF
   ```

   `proposed` 只登记意图，旧决策继续生效。

5. **提交时带上 trailer**，用命令打印出来的完整 ID：

   ```
   Decision: D-<完整 uuid>
   ```

## 不要做的事

- 不要为了让门禁通过而新建一个空的或不相关的决策，`keel check` 会识别出来。
- 不要在 trailer 里写短前缀。
- 不要把「还没验证的猜测」写成决策，那是 `keel note`。
