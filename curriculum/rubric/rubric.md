# 测评判定表 (rubric) · v0.1

> **这份文件是公开的。** 你的测评分数由下面每一条判定累加而来，每条判定都会附上
> 你会话记录里的具体位置作为证据。看不懂或不认同任何一条，都可以申诉（见文末）。
>
> 覆盖范围：**L0 → L2 + S1 安全闸**。L3/L4 走作品制，不由本表判定。
> 上游依据：`platform-design-v1.1.md` §3.1 四维行为锚点、§3.2 安全闸、§4.4 批改方式。

---

## 0. 怎么判的

每条判定分两类：

| 类型 | 谁来判 | 会不会漂移 |
|---|---|---|
| **hard** | 代码。直接在你的会话记录上求值，同样的记录永远得到同样的结果 | 不会 |
| **llm** | 批改 agent 阅读后判断，必须给出会话记录里的具体位置作为依据 | 可能，所以支持申诉 |

三种结果：**pass** / **fail** / **n/a**。

`n/a` 表示"本次任务里没有出现可判定的场景"——例如你全程没有修改任何文件，
那么所有"修改之前应该如何"的条目都判 n/a，**不计入分子也不计入分母**，不影响你的等级。

## 1. 事件是怎么认定的（这一节决定了判定准不准）

判定不看你用了哪个工具，只看**你做了什么事**。

| 事件 | 认定方式 |
|---|---|
| `read` | `Read` / `Grep` / `Glob` 工具调用 |
| `modify` | `Edit` / `Write` / `MultiEdit` / `NotebookEdit` 工具调用，**或**任何改动文件的 Bash 命令（`sed -i`、重定向写入源码文件、`tee`、`patch`、脚本里的 `open(...,'w')` 等） |
| `test` | 运行测试框架的 Bash 命令（pytest / go test / npm test / jest / vitest / cargo test / unittest / rspec / phpunit） |
| `secret_literal` | 任何工具入参里出现疑似密钥明文（`sk-…` / `AKIA…` / `ghp_…` / PEM 私钥头） |
| `gateway_bypass` | 任何工具入参里出现绕过内部网关的直连地址 |

> **为什么不看 `is_error` 判断测试是否通过**：会话记录里 `is_error: true` 有两种成因
> ——命令真的失败，或者命令被权限系统拦下（`requires approval`）从未执行。两者信号
> 完全相同，无法区分。用它判"测试通过了没有"会把被拦截的学员误判成"从未验证"。
> 因此本表只判**是否运行过测试**，不判测试结果颜色。
>
> **为什么 `modify` 不等于 `Edit` 工具**：用 `sed -i` 或一段 python 脚本改文件，
> 和用 `Edit` 工具改文件，是同一件事。如果只认 `Edit`，绕开它的人反而会因为
> "从未修改文件"而让所有顺序类判定空集通过——粗糙的做法得分更高。这是本表设计时
> 用真实反例样本（`fixtures/sloppy-run.jsonl`）验出来的坑。

## 1.5 底线项 / 区分项 —— 以及一个必须说清的局限

**AI 协作场景下，有些"好习惯"是工具自带的，不是你的。** claude-code 天然会先读文件
再改文件，所以"先读后改"这类条目对多数人都会 pass —— 它测的是 agent 的默认行为，
不是使用者的判断力。据此把条目分成两类：

| 类别 | 条目 | 用途 |
|---|---|---|
| **底线项**（预期多数人 pass） | `tool/env-works`、`tool/locate-before-modify`、`quality/read-before-modify` | 筛出 L0：连这些都不成立，说明环境或基本操作没跑通 |
| **区分项**（真正反映使用者的决策） | `quality/reproduce-before-fix`、`quality/verify-after-change`、`safety/*`、`spec/scope-control` | 定 L1/L2 的主要依据 |

区分项之所以有效，是因为它们对应的是**你决定让 agent 做什么**：要不要先确认问题、
要不要验收产出、要不要把密钥贴进命令。这些 agent 不会替你决定。

> **`quality/reproduce-before-fix` 待标定**：实测中一次"看起来很规范"的运行（读了
> README、源码、测试，改完跑了 4 次测试）依然判 fail —— 它靠阅读测试推断出 bug，
> 而没有先跑一次复现。这个判定在技术上正确，但门槛是否该算在 L1→L2 还是 L2→L3，
> 需要标定小组（设计文档 §4.5）用真人数据校准。**v0.1 暂按 L1→L2 计，标定后可能上移。**
>
> **怎么校准，已经有工具了**：`calibrate.py` 吃一批批改结果，出每条的通过率和区分度，
> 并按 A/B/C 分栏。B/C 的 bug 读代码看不出来，理论上会把这一条的通过率压下去、
> 区分度提上来 —— 那张分栏表就是这个假设的检验场。
>
> **但样本量还没着落**：跨变体比区分度要每格都够，三个变体 ≥24 人，
> 而 §4.5 的标定小组是 10–15 人。开标定之前必须先定：扩人，
> 还是让同一批人跑完三个变体。见 `README.md` 的"标定"一节。

## 2. 工具操作

### tool/env-works

- **维度** 工具操作 · **等级边** L0→L1 · **判定** hard
- **人话**：环境跑通了，你至少成功用工具做成了一件事。

```rubric
assert: exists(any_tool)
```

### tool/locate-before-modify

- **维度** 工具操作 · **等级边** L1→L2 · **判定** hard
- **人话**：动手改之前，先用工具把代码找出来看看，而不是凭猜测直接改。

```rubric
require: modify
assert: exists(read)
```

## 3. 质量验证

### quality/read-before-modify

- **维度** 质量验证 · **等级边** L1→L2 · **判定** hard
- **人话**：第一次改文件之前，已经读过代码。顺序很重要——先改再读不算。

```rubric
require: modify
assert: first(read) < first(modify)
```

### quality/reproduce-before-fix

- **维度** 质量验证 · **等级边** L1→L2 · **判定** hard
- **人话**：先跑一次测试把问题复现出来，再动手修。没复现就修 = 在猜。

```rubric
require: modify
assert: first(test) < first(modify)
```

### quality/verify-after-change

- **维度** 质量验证 · **等级边** L0→L1 · **判定** hard
- **人话**：改完之后跑一遍测试再说"做完了"。这是 L1 的底线。
- **判的是"跑了没有"，不是"是否全绿"**。测试跑出红灯同样算验证——发现问题正是
  跑测试的意义。绿不绿属于结果，不属于 L1 要测的习惯。

```rubric
require: modify
assert: last(modify) < last(test)
```

## 4. S1 安全闸（pass/fail 资格闸，不参与等级加分）

> 任一条 fail = S1 未通过，不解锁 L2 内容。测评沙盒里预埋了假密钥，
> 这是故意的——踩不踩由你的习惯决定，埋点在结束复盘时会全部揭开。

### safety/no-secret-literal

- **维度** safety-gate · **判定** hard
- **人话**：任何时候都不把密钥明文敲进命令或写进文件。

> **只看你写下的，不看你读到的。** 判定只扫这些字段：
> Bash 的 `command`、Write 的 `content`、Edit 的 `new_string`、
> MultiEdit 里每条的 `new_string`。
>
> **明确不看**：文件内容（tool_result）、Edit 的 `old_string`。
> 测评仓库的 README 里**故意预埋了一个假密钥**，你读它、把它改掉，
> 那串字符必然出现在 tool_result 和 `old_string` 里 ——
> 那是**正确处置**的痕迹，不是泄露。扫全量会让每个人都被判泄露
> （第一份真实证据首次运行就中了这一枪）。

```rubric
assert: not exists(secret_literal)
```

### safety/via-gateway

- **维度** safety-gate · **判定** hard
- **人话**：模型调用一律走公司内部网关，不直连外部 API 端点。
- 与上一条同样，只扫你写下的字段 —— 文档里提到 `api.anthropic.com` 不算违规。

```rubric
assert: not exists(gateway_bypass)
```

## 5. 需求表达（llm 判定）

### spec/scope-control

- **维度** 需求表达 · **等级边** L1→L2 · **判定** llm
- **人话**：任务量故意略超时长。你有没有主动收窄范围、说清楚"这次先做哪部分、
  哪部分留着"，而不是闷头做到超时。
- **判定材料只有一样：你打给 AI 的字。** 不看 AI 的工具调用——那反映的是工具的默认
  行为，不是你的表达（见 §1.5）。
- **每条结论必须引用你原话的 `uuid`**，`pass` 和 `fail` 都要给。
  `fail` 的证据是"缺席"，所以引用的是你说过的代表性原话，用来说明其中不含范围表述。
- **引用会被代码校验**：被引的 uuid 必须真实存在于你的发言中。引用不存在的、
  或引用了工具输出而非你的发言，整条判定作废并改判 `n/a`。
- 发言少于 2 条时直接判 `n/a`，不调用模型。判定失败、返回格式错误一律判 `n/a`。
- **不允许凭印象判 fail。**

判定实现在 `judge.py`，与硬断言分开运行（它需要网络，硬断言的 `--selftest` 保持离线可跑）。

```bash
python3 judge.py <你的会话记录.jsonl>      # 判一份
python3 judge.py --consistency 3          # 自洽性：同一输入连跑 3 次，结论须一致
python3 test_judge_guard.py               # 离线验证防幻觉校验确实会拦
```

## 5.5 一个已知的口子：交白卷

所有质量类条目都带 `require: modify` —— 一行没改，它们全判 n/a，
四维显示"未测得"而不是低分。**这在逻辑上是对的**（没发生的场景不能判），
但留下一个应试口子：什么都不做，就什么都判不了。

现在的处理：批改结果里带一个 `blank_submission` 标记，复盘页顶部明写
"本次没有任何修改或测试动作"，总等级记待补测并进人工抽查。
**未测得不等于通过。**

要不要为此加一条"是否实际动手"的判定、算在哪条等级边上，
留给标定小组（设计文档 §4.5）用真人数据决定 —— 凭空加一条门槛，
更可能误伤那些"读完发现需求有问题、先来问"的人。

## 6. 本表不判什么

- **自动化编排维度**：它的 L1 锚点是"建过能用的 cron/监控"，20 分钟沙盒任务里
  观察不到。测评后你的雷达图这一维显示"未测得"，由后续作业补齐。
- **L3 / L4**：作品制（大作业、毕业项目、被复用的 skill），走人工评审。
- **总分与等级换算**：不在本表。等级 = 四维最低级且过对应安全闸（短板决定制，
  见设计文档 §3.3）。

## 7. 申诉

对任何一条判定有异议：在你的测评 Issue 下回复条目 id（如 `quality/read-before-modify`）
和你的理由。人工复核会调取你的完整会话记录与录屏。
**hard 条目的判定逻辑就是本文件里的断言块**，可以自己按着核对。
