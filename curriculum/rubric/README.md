# rubric —— 判定表与批改 agent

```
rubric.md              公开的判定表。改它就是改批改逻辑。
score.py               硬断言求值（离线，无网络）
judge.py               需求表达的 llm 判定（要网关）
grade.py               聚合成四维向量 + S1 + 证据 + 复盘
calibrate.py           一批批改结果 → 每条判定的难度和区分度（标定小组用）
test_grade_rules.py    聚合规则的离线测试
test_judge_guard.py    llm 防幻觉校验的离线测试
test_calibrate.py      区分度算法的离线测试（合成数据，不是标定结论）
fixtures/              样本 + 期望值
```

## 跑法

```bash
python3 grade.py <harvest 目录> --student <学员> --out <目录>
python3 grade.py --transcript <x.jsonl> --student <学员> --no-llm   # 离线

python3 score.py --selftest        # 硬断言未被改坏
python3 test_grade_rules.py        # 聚合规则
python3 test_judge_guard.py        # 防幻觉校验
python3 test_calibrate.py          # 区分度算法
```

## 标定：一批人跑完之后

```bash
python3 calibrate.py ~/.local/state/microclass/evidence/*        # 每人取最新一批批改
python3 calibrate.py <harvest 目录>... <grade.json>... [--json]
python3 calibrate.py run-hasty.jsonl=a                           # 裸 transcript 要标变体
```

出每条判定的**难度**（通过率）和**区分度**（D = 上组通过率 − 下组通过率，
以及点二列相关 r_pb），并按 A/B/C 分栏 —— 那张分栏表就是"B/C 的 bug
更难一眼看穿，所以 `reproduce-before-fix` 区分度更真实"这个假设的检验场。

三条设计决定，都是为了防止它自己变成噪声源：

- **样本不够时一个区分度都不算**，只出计数，并明说还差多少人。
  在 n=3 上算出来的 D 看着像证据，其实是噪声，而且从此没人再去补样本。
- **分组用的总分扣掉了本条**。只有 7 条判定，拿含本条的总分分组等于用答案
  给自己分组，每条都会显得很有区分度 —— 短测验里最常见的自欺。
- **全体同判的条目不判"坏"**，只报"区分度结构上为 0"。底线项本来就该大多数人
  过（rubric §1.5），把它当没用删掉是误读。

### 它算出来的第一件事：10–15 人不够

跨变体比区分度要求**每个变体各有足够样本**，不是总数够就行。
按 `calibrate.py` 的下限（每格 ≥8），三个变体要 ≥24 人，
而设计文档 §4.5 的标定小组是 10–15 人 —— 分到三轨每轨 3–5 人，算不出结论。

两条路，**必须先选一条再开标定**，否则跑完才发现数据答不了问题：

- 扩到 24 人以上；
- 或让同一批人把三个变体都跑一遍（受试者内设计，样本效率高得多；
  代价是第二、三次带练习效应，得把顺序在人之间轮换开）。

或者走 skill：`platform/skills/microclass-grade/run.sh <学员>`。

## 维度和等级边不在代码里

`grade.py` 从 rubric.md 每条的 `**维度** X · **等级边** L1→L2 · **判定** hard`
那行读出来。改 rubric 就改了批改逻辑，两处不会漂（设计文档 §4.4）。

## 聚合规则：四件容易写错的事

写这套聚合时，**期望值先于实现写下**（`test_grade_rules.py`），
不然断言很容易被调成"能过"。四个坑：

### 1. 空集不算通过

一条等级边上的条目**全是 n/a** 时，既不能判过（空集上的断言天然成立），
也不能判 L0（那是冤枉人）—— 只能是"未测得"。

### 2. 过了高的隐含低的，没过不能反推低的

阶梯语义是不对称的：

- 能收窄范围的人，不可能说不清一句话 → **只要有一条边判过，等级就取它**，
  更低那条测没测都不影响。
- "没升到 L2" ≠ "就是 L1" —— 除非 L0→L1 那一级**真的判过**。

需求表达正好撞上后一种：rubric 只实现了 L1→L2，
设计文档 §3.1 里那条 L1 锚点（"一句话说清任务"）**还没落成条目**。
所以 `spec/scope-control` 判 fail 时，只能得出"上限不超过 L1"，下限未知。

> 这条是写测试时才发现的。我第一版期望值写的是 L1 —— 等于把"没升到 L2"
> 当成了"就是 L1"，悄悄替学员认领了一级没测过的能力。
> **rubric 缺 需求表达 的 L0→L1 锚点，是个真缺口**，记在这里等标定小组补。

### 3. 有洞的向量不能取 min

短板决定制（§3.3）要求四维取最低。但 `自动化编排` 在 20 分钟沙盒里观察不到
（rubric §6），测评后向量必然有洞 —— 这时总等级只能是 **待补测**。

唯一例外：已测得的维度里已经出现 L0。那已经是最低了，补测不可能更低，
结论可以当场下，不必让学员干等。

### 4. S1 是资格闸不是分数

任一安全条目 fail → 不改任何一维的等级，**只封顶总等级**（§3.2）。
把它做成扣分会让"密钥泄露"和"少跑了个测试"变成同一种东西。

## 多会话必须合并判定

学员一场测评通常有多个会话：`/clear` 之后重开、`claude -p` 顺手问一句、
断线后 `--continue`。`grade.py` 把 harvest 里**全部**会话按时间接起来再判。

**不能只取一份。** 早先的实现取"最大的那份"，是个静默的任意选择，两个方向都会错：

| 情形 | 只取一份的结果 |
|---|---|
| 会话 A 读了文件，会话 B 才改 | 只看 B → `read-before-modify` **误判 fail** |
| 随手问一句的短会话碰巧最大 | 判的根本不是那份作业 |

`fixtures/multi/` 钉住了第一种：A 只读+跑测试、B 只改+跑测试，
正确答案是三条 quality 全 pass。实测只看 B 时两条 fail，合并后全 pass。

`grade.json` 里 `session_count` 和 `sessions` 记着合并了哪几份。

## 两个必须显性化的异常

| 字段 | 含义 | 怎么处理 |
|---|---|---|
| `rubric_items_missing` | rubric 里有这条，打分器没产出结果 | **代码 bug**，修好再批 |
| `blank_submission` | 整场没有任何修改/测试动作 | 未测得**不等于**通过，进人工抽查 |

`--no-llm` 时 llm 条目记 `guard: skipped-no-llm`，**不进** `rubric_items_missing` ——
故意跳过和真漂移是两回事，狼来了喊多了就没人看了。
（两个方向都验过：`--no-llm` 不误报；往 rubric 里塞一条新条目，告警照响。）

## 已知局限

- **需求表达缺 L0→L1 锚点**（见上）。
- **`quality/reproduce-before-fix` 待标定**：一次看起来很规范的运行仍判 fail
  （它读测试推断而非先复现）。判定技术上正确，但门槛该算 L1→L2 还是 L2→L3，
  等标定小组定。
- **`spec/scope-control` 需要多轮真人会话**。`simulate.py` 用 `claude -p` 单发一句，
  学员发言只有 1 条，judge 直接判 n/a（`skipped-no-api-call`）。
  这是模拟的局限，不是判定的 —— 真实测评是 20 分钟交互式多轮。
- **`not exists` 类条目通过时没有证据**（`safety/via-gateway` 证据 0 条）。
  "没发生"本来就没有正面痕迹。fail 时才有。
